一项真实工作经常需要不止一种能力。

例如发布一篇带配图的教程，可能包括：

```text
调研来源
→ 设计内容结构
→ 撰写和编辑
→ 生成两种图片
→ 压缩图片
→ 构建网站
→ 检查线上页面
```

这不代表你应该安装一个“万能内容 Skill”，也不代表要把所有相关 Skill 同时点亮。

复杂工作流最容易失败的地方，往往不是能力不够，而是：

- 两个 Skill 都认为自己应该主导；
- 上一步没有交付清楚的结果；
- 工具、Skill 和 Agent 的职责混在一起；
- 中途失败后仍继续发布；
- 高风险动作没有人工确认；
- 一次暴露太多相似 Skill，路由变得不稳定。

组合的核心不是“数量”，而是“分工和交接”。

![一个主负责 Skill 调度研究、写作、图片和发布辅助能力，并通过清晰交接物与人工确认点串联](/images/docs/skills/compose-multiple-skills-illustration.webp)

## 先分清四种角色

在组合之前，先把参与者分成四类。

### Skill：保存怎么做

Skill 提供一类任务的稳定方法，例如：

- 如何做来源清楚的调研；
- 如何写符合本站结构的文章；
- 如何检查前端页面；
- 如何完成发布前验收。

### 工具或 MCP：负责拿数据和行动

它们可以：

- 搜索网页；
- 读取文件或数据库；
- 控制浏览器；
- 访问 GitHub、Notion 或其他 App；
- 部署、发消息或修改外部系统。

Skill 可以告诉 Agent 何时、为什么、怎样使用工具，但 Skill 本身不等于外部连接。

### Agent：理解目标并做判断

Agent 负责读取当前任务、选择方法、调用工具、处理失败并形成结果。

### Subagent：拆分独立工作

当任务可以并行、需要隔离上下文或需要不同专业判断时，主 Agent 可能把具体子任务交给 Subagent。

不是每个多 Skill 工作流都需要 Subagent。顺序清楚的小流程，一个 Agent 也可以逐步完成。

如果仍然容易混淆，先回看[Skill、Prompt、Project、Memory、MCP 的区别](/docs/skills/skill-vs-prompt-project-memory-mcp)。

## 一条最重要的规则：只有一个主负责人

一次任务可以使用多个 Skill，但最好只有一个 Skill 定义整体完成标准。

例如“发布 Skills 教程”：

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 主负责人：文章发布流程 | 阶段顺序、完成标准、停止条件、最终 QA | 不替代专业调研或图片方法 |
| 调研 Skill | 找来源、核对事实、记录证据 | 不直接发布文章 |
| 写作 Skill | 结构、正文、编辑和读者表达 | 不凭空决定事实 |
| 图片 Skill | 正文图、漫画图和视觉验收 | 不改变文章结论 |
| 部署 Skill | 构建、发布、线上冒烟测试 | 不在构建失败时强行上线 |

主负责人可以是：

- 本次 Prompt 中明确写出的计划；
- 一个项目级工作流 Skill；
- 人工维护的检查清单。

不一定非要再创建一个“总控 Skill”。只有当同一组合流程反复执行、顺序和验收长期稳定时，才值得沉淀。

## 三种常见组合方式

### 1. 顺序流水线

上一步的结果是下一步的输入。

```text
调研简报
→ 文章大纲
→ 完整正文
→ 图片内容简报
→ 图片文件
→ 构建产物
→ 线上验收
```

最适合：写作、发布、数据处理、审计和报告生成。

风险是前面的错误一路传下去。每个交接点都要有最小检查。

### 2. 并行分支

多个相互独立的子任务同时进行，最后合并。

```text
                 ┌→ 核对官方文档 ─┐
研究问题与范围 ──┼→ 收集社区问题 ─┼→ 综合研究简报
                 └→ 盘点现有内容 ─┘
```

最适合：独立来源调研、多个页面检查、互不修改同一文件的任务。

并行不是 Skill 自动拥有的能力。是否由一个 Agent 顺序完成，还是交给多个 Subagent，取决于当前客户端、任务边界和可用工具。

### 3. 条件分支

只有满足条件时才调用某项能力。

```text
构建通过？
├─ 否 → 修复构建，不部署
└─ 是 → 部署
         └→ 线上检查失败？回滚或修复
```

最适合：安全、发布、审批、支付和数据质量流程。

条件应该可以观察，例如退出码、测试结果、文件是否存在或人工是否批准，而不是“感觉差不多”。

## 用交接契约连接 Skill

不要只写：

```text
先调研，然后写文章，再配图。
```

每一步至少定义四项：

```text
输入：从哪里来
输出：交付什么
验收：怎样算通过
失败：不通过时怎么办
```

例如调研到写作的交接：

| 项目 | 契约 |
| --- | --- |
| 输入 | 研究问题、现有文章列表、时间范围 |
| 输出 | 候选主题、来源 URL、事实摘要、争议和未知项 |
| 验收 | 关键事实至少有官方或原始来源，社区只作讨论信号 |
| 失败 | 找不到可靠来源时标记未知，不进入正文结论 |

写作到图片的交接：

| 项目 | 契约 |
| --- | --- |
| 输入 | 已完成并审核的全文 |
| 输出 | 核心观点、关键步骤、边界、两张图的不同职责 |
| 验收 | 图片不虚构文章里没有的数字、功能或结论 |
| 失败 | 文章仍在变化时暂停生成，先稳定事实 |

交接契约让你可以替换某个 Skill，而不必重写整条工作流。

## 怎样处理重叠

Firecrawl 调研和 OpenAI Community 讨论中，较大的 Skill 目录经常遇到语义重叠。

处理时使用“所有权 + 辅助能力”而不是“谁优先级更高”。

### 错误组合

```text
frontend-design：负责设计页面
ui-polish：负责把页面设计得更好
web-design：负责做更专业的设计
```

三者没有可以观察的边界。

### 更清楚的分工

```text
frontend-design：从需求创建新页面和视觉方向
web-design-guidelines：审查已有页面的可用性与规范问题
browser-qa：在真实浏览器验证交互、断点和错误
```

判断两个 Skill 是否应该同时存在，可以问：

1. 它们是否拥有不同输入？
2. 是否交付不同结果？
3. 是否在不同阶段使用？
4. 一个移除后，另一个能否完整替代？
5. 能否用一句话说明谁主负责、谁辅助？

如果答案大多是否定的，考虑合并、拆分或禁用其中一个。

## 不要让“路由 Skill”无限长大

有些团队会创建一个总路由 Skill，列出几十个其他 Skill 和优先级。

小规模时可能有用，但它容易产生三个问题：

- 每增加一个 Skill 都要同步路由规则；
- 路由说明本身占用上下文；
- 静态规则很快和当前可用目录不一致。

更耐用的做法是：

- 每个 Skill 自己写清触发范围和相邻边界；
- 项目只保留必要能力；
- 工作流 Skill 只描述固定阶段和交接物；
- 临时组合写在本次 Prompt 或执行计划里；
- 大型目录定期删除重复、废弃和长期不用的项。

## 组合 Skill 与 MCP

MCP 适合连接外部数据和动作，Skill 适合保存使用这些能力的方法。

例如电商评论分析：

```text
评论分析 Skill
负责：字段检查、主题分类、证据引用、报告结构和 QA

Shopify / 数据库 / 表格连接
负责：提供真实订单、商品和评论数据

人工确认
负责：批准发布、改价、退款或营销动作
```

不要把连接能力写成假设。Skill 依赖某个 MCP、App、CLI 或 API 时，应明确：

- 依赖名称；
- 需要的权限；
- 缺失时如何提示；
- 是否有只读或离线替代路径；
- 哪些动作必须人工确认。

## 组合后的错误怎么处理

每一步失败后，默认不要假装成功继续传递。

使用三种结果：

```text
通过：输出满足契约，可以继续
可降级：缺少非关键能力，使用明确替代方案继续
阻塞：关键输入、权限或验收失败，停止并报告
```

例如网页调研失败：

- 如果已有官方文档缓存，可以标记日期后继续；
- 如果文章要求“最新价格”，无法联网就是阻塞；
- 不应该让写作 Skill 用记忆补出一个看似完整的价格表。

## 怎样测试组合工作流

先单独测试每个 Skill，再测试交接，最后测试整条链。

### 1. 单项测试

确认每个 Skill 在自己的最小任务上正常。

### 2. 交接测试

检查上一步输出是否真的包含下一步所需字段。

### 3. 失败测试

主动制造：

- 缺少来源；
- 图片生成失败；
- 构建退出码不为 0；
- 外部权限被拒绝；
- 人工不批准发布。

确认流程会停止或降级，而不是跳过。

### 4. 整体回归

保存一项代表性真实任务。修改任何 Skill 或工具连接后，重新运行关键阶段。

## 一个完整例子：发布 Skills 教程

```text
1. 主负责人读取现有目录，定义内容缺口和完成标准
2. Firecrawl 调研 Skill 搜索官方来源和社区讨论信号
3. 写作 Skill 依据研究简报完成结构和全文
4. 人工检查事实、重复度和小白可读性
5. ImageGen 工作流读取定稿文章，分别生成正文图与漫画图
6. 图片压缩流程输出 WebP，并检查尺寸和可读性
7. 项目构建流程运行内容、类型、路由和内部链接检查
8. 人工批准后部署
9. 浏览器或 HTTP 工具验证文章、图片和移动端
```

这里没有任何一个 Skill “包办全部”。可靠性来自每一步职责清楚、输出可检查、失败不会被掩盖。

![女生向导先指定主负责人，再安排顺序、并行和条件分支，检查交接物并在发布前人工确认的五步漫画](/images/docs/skills/compose-multiple-skills-comic.webp)

## 组合前检查表

- [ ] 只有一个整体主负责人
- [ ] 每个 Skill 拥有不同任务或阶段
- [ ] 工具和 MCP 只负责数据与动作，不冒充方法
- [ ] 每一步有输入、输出、验收和失败处理
- [ ] 相邻 Skill 的所有权边界可以用一句话解释
- [ ] 高风险动作有人工确认
- [ ] 单个 Skill、交接和整体链都被测试
- [ ] 临时组合没有过早沉淀成庞大路由 Skill
