学 AI 工具时，很容易遇到一堆看起来差不多的词：

**Prompt、Memory、Project、Skill、MCP、App、Agent……**

如果只看产品介绍，很容易越看越乱。

其实这些东西并不是在互相替代，而是在解决**不同层的问题**。

这一篇不追求技术定义，而是先帮你建立一张工作地图。

<span id="one-sentence-map"></span>

## 先记住这一张地图

先不用记任何复杂概念，只记下面六句话：

| 概念 | 最简单的理解 | 它回答的问题 |
| --- | --- | --- |
| Prompt | 当前任务 | **这次要做什么？** |
| Memory | 关于你的长期信息 | **你是谁、你偏好什么？** |
| Project | 某项长期工作的上下文 | **我们现在在做什么项目？** |
| Skill | 可复用的工作方法 | **这类事情应该怎么做？** |
| MCP / App | 外部数据与操作能力 | **去哪里拿信息、能操作什么？** |
| Agent | 把目标、上下文、方法和工具组合起来执行 | **怎样把整件事完成？** |

如果你只想快速建立概念，到这里其实已经够了。

下面我们用同一个例子把它们拆开。

假设你是一名销售，要准备明天和一家潜在客户的会议。

<span id="prompt"></span>

## Prompt：这次做什么

Prompt 是最接近“任务指令”的一层。

例如：

```text
帮我准备明天和 Acme 的客户会议，
重点关注他们最近半年的业务变化和可能遇到的问题。
```

这里的信息主要属于**这一次任务**：

- 客户是 Acme；
- 会议在明天；
- 关注最近半年；
- 希望研究业务变化和潜在问题。

换一个客户，这段 Prompt 自然会跟着变。

所以可以记成：

> **Prompt = 这一次我要你做什么。**

<span id="memory"></span>

## Memory：记住关于你的信息

有些信息不是只对一次任务有用，而是关于你本人。

例如你可能长期偏好：

- 汇报先给结论，再给细节；
- 不喜欢过度正式的文字；
- 金额默认同时展示人民币和美元；
- 做分析时希望明确区分事实与推测。

这些属于“关于你”的长期信息，更接近 Memory 的职责。

所以可以记成：

> **Memory = 记住我是谁，以及我长期有什么偏好。**

Memory 不适合拿来保存一套几十步的销售研究流程。

因为“我喜欢简洁表达”和“销售会前研究应该先查什么再查什么”，本质上是两种不同的信息。

<span id="project"></span>

## Project：长期工作的上下文

现在假设 Acme 不是一次性客户，而是你正在跟进三个月的重点客户。

你已经有：

- 客户背景资料；
- 历史会议纪要；
- 报价方案；
- 内部讨论；
- 之前的邮件；
- 当前推进阶段。

这些东西属于**这个客户 / 这个项目本身的上下文**。

它们不应该成为你的个人 Memory，也不是“所有客户都通用”的 Skill。

所以可以把 Project 理解成：

> **Project = 围绕一项长期工作，把相关聊天、文件和上下文放在一起。**

换一个客户，Project 里的材料也会跟着换。

<span id="skill"></span>

## Skill：这类工作怎么做

现在再看“销售会前研究”这件事。

无论客户是 Acme、Nike 还是一家刚成立的创业公司，你可能都希望 AI 遵循类似的方法：

1. 先确认公司是谁；
2. 了解产品和商业模式；
3. 找最近的重要动态；
4. 判断可能的业务挑战；
5. 区分公开事实与合理推测；
6. 根据客户情况生成会议问题；
7. 最后输出一页会前 Brief。

这套方法并不属于某个客户。

它属于：

> **“销售会前研究这类工作应该怎么做。”**

这就是 Skill 最适合承载的东西。

所以记成：

> **Skill = 这类事情以后应该按照什么方法完成。**

这也是为什么 Skill 更像 SOP，而不是单次 Prompt。

<span id="mcp"></span>

## MCP / App：去哪里拿数据和行动

接下来又会遇到一个问题：

AI 知道“应该研究客户”，但**客户资料在哪里？**

可能在：

- Gmail；
- Google Drive；
- Slack；
- CRM；
- Notion；
- 公司数据库；
- 某个内部系统。

如果 AI 需要连接这些外部系统去读取信息，甚至执行操作，就进入了 App、Connector 或 MCP 这类能力的范围。

对小白来说，不必一开始研究协议细节。

先记住：

> **Skill 主要告诉 AI“怎么做”；MCP / App 主要让 AI“能去哪里拿数据、能操作什么”。**

例如：

```text
Skill：
告诉 AI 怎样做销售会前研究。

Gmail / CRM App：
让 AI 能看到过去和这个客户的邮件与销售记录。
```

只有工具，没有方法，AI 可能知道很多信息但不知道怎样组织。

只有方法，没有数据，AI 又可能缺少完成任务所需的上下文。

两者可以组合。

<span id="agent"></span>

## Agent：把这些能力组合起来

Agent 是更上层的概念。

当 AI 不只是回答一个问题，而是为了一个目标：

- 自己判断下一步；
- 使用 Skill；
- 查找项目资料；
- 调用外部工具；
- 执行多个步骤；
- 检查结果；
- 最终交付成果；

你就开始进入 Agent 式工作方式。

可以用一个员工来类比：

```text
Prompt  = 你今天交代给他的任务
Memory  = 他记得你的偏好
Project = 他手上的项目档案
Skill   = 他的 SOP 和专业方法
MCP/App = 他能使用的业务系统和工具
Agent   = 这个能够综合以上信息去完成工作的员工
```

这个比喻不是严格的技术定义，但对于建立直觉非常有用。

<span id="real-example"></span>

## 放到一个真实工作里看

假设你是电商运营，希望 AI 每周自动分析店铺表现。

这几个概念可以这样分工：

### Prompt

```text
分析 8 月 1 日到 8 月 7 日的数据，
这周重点看广告转化下降的问题。
```

这是本周特有的任务。

### Memory

```text
我喜欢先看结论；
百分比统一保留一位小数；
没有证据的原因必须标记为假设。
```

这是你的长期偏好。

### Project

里面放：

- 这个店铺的产品资料；
- 历史周报；
- 活动计划；
- 目标 KPI；
- 团队讨论。

这是当前业务的长期上下文。

### Skill

规定每次周报都：

1. 检查 GMV、流量、转化率；
2. 找环比异常；
3. 下钻广告和商品；
4. 分析可能原因；
5. 区分事实和假设；
6. 给出下周动作；
7. 按统一模板输出。

这是可复用的方法。

### MCP / App

让 AI 可以读取：

- 数据表；
- 广告后台；
- CRM；
- Google Drive。

这是数据和操作能力。

### Agent

最后，你可以让一个 Agent 把这些能力串起来：

> 读取本周数据 → 调用周报 Skill → 找异常 → 必要时继续查资料 → 生成周报。

这时你会发现，它们不是六个互相竞争的产品名词。

**它们是同一个 AI 工作系统里的不同层。**

<span id="how-to-choose"></span>

## 到底应该怎么选

遇到一个需求时，可以按下面的顺序判断：

**只是这次要 AI 做一件事？**

→ 先用 **Prompt**。

**希望 AI 长期记住关于你的偏好？**

→ 考虑 **Memory**。

**有一项长期项目，需要持续使用同一批文件和聊天？**

→ 放进 **Project**。

**同一类工作反复出现，而且希望按照固定方法完成？**

→ 做成 **Skill**。

**任务需要读取外部系统的数据，或者执行操作？**

→ 需要 **App / Connector / MCP** 一类能力。

**任务需要自己完成多个步骤，并根据结果继续行动？**

→ 开始考虑 **Agent**。

现实工作里，它们通常不是二选一，而是组合使用。

例如一句：

> “帮我准备明天的客户会议。”

背后完全可能同时使用 Project 的客户资料、Memory 的个人偏好、销售研究 Skill，以及 Gmail / CRM 的外部数据。

这也是 Skill 值得单独学习的原因：

**它承载的是你的工作方法，而工作方法正是从“会问 AI”走向“让 AI 真正帮你工作”的关键一层。**
