第一次知道 Skill 的人，很容易立刻去搜索：

> 最值得安装的 100 个 Skill 是什么？

这通常不是一个好起点。

一个目录里即使有成千上万个 Skill，真正适合你当前工作的可能只有一两个。装得越多，也不代表 AI 越聪明；范围相似的 Skill 反而可能让选择变得模糊，也会增加审查和维护成本。

更稳妥的顺序是：

```text
先定义任务
→ 从可信来源找候选
→ 检查质量与风险
→ 安装到正确范围
→ 用一件小任务验收
→ 决定保留、禁用或删除
```

这篇不会提供一张很快过期的“必装榜单”，而是给你一套以后都能重复使用的选择方法。

![从任务需求、可信来源、质量检查到小范围安装与真实任务验收的 Skill 选择漏斗](/images/docs/skills/discover-and-install-skills-illustration.webp)

## 搜索前先写一张任务卡

不要先搜 Skill 名字。先用四句话说明你真正要完成什么：

```text
任务：每周分析一次网站运营数据
输入：CSV、上周数据和活动记录
输出：异常、证据、可能原因和下周动作
边界：不自动修改广告预算，不把猜测写成事实
```

这张任务卡会帮你排除很多“看起来很强、实际不匹配”的候选。

例如你的目标是分析 CSV，就不必安装一个涵盖数据库、爬虫、广告投放、邮件发送和项目管理的巨大 Skill 包。先找一个能稳定完成数据检查与分析的 Skill，更容易判断它有没有价值。

## 从哪里找 Skill

可以把来源分成四层，越靠前越适合新手优先检查。

### 1. 当前产品已经提供的 Skill

先看 ChatGPT、Codex 或当前工作区的 Skill 选择器。

系统 Skill 通常已经随产品提供，不需要复制陌生命令或下载额外文件。第一次体验时，优先从这里选择文档、表格、PDF、图片或浏览器等与你任务直接相关的能力。

### 2. 官方或维护者仓库

如果任务依赖某个产品，优先查它自己的文档和代码仓库。

例如支付、数据库、部署或设计系统的维护者，可能会提供与产品同步更新的 Skill。官方来源不等于可以跳过审查，但作者、版本和问题反馈通常更容易追踪。

### 3. 团队或项目仓库

项目级 Skill 往往最贴合实际工作，因为它可以保存：

- 当前仓库的目录和技术约定；
- 构建、测试和发布命令；
- 业务状态、数据来源和安全边界；
- 团队约定的输出格式与 QA。

如果同事已经在仓库的 `.agents/skills/` 中维护了 Skill，先理解并复用它，不要再安装一个功能相同的社区版本。

### 4. 社区目录与市场

社区目录适合发现新方案，但搜索排名、星标、下载量和“热门”徽章只能帮助你建立候选列表，不能证明 Skill 安全或适合你的任务。

Firecrawl 调研中，“如何发现 Skill”“哪个目录更全”“该安装哪些”反复出现在 Codex、Claude Code 和 Agent Skills 社区；与此同时，原始安全研究也表明，公开目录需要像软件包市场一样认真审查。

所以社区来源的正确用法是：

> 用它发现候选，用源码、维护记录和真实测试做决定。

## 用七个问题筛选候选

看到一个 Skill 后，先不要运行安装命令。

### 1. 它解决的任务具体吗

好的描述会说明：

- 什么时候应该使用；
- 处理什么输入；
- 交付什么结果；
- 哪些相邻任务不属于它。

“让你的工作效率提升十倍”无法验证。“审查 React 页面中的可访问性、交互状态和移动端问题”就清楚得多。

### 2. 来源和维护者能追踪吗

检查：

- 作者或组织是谁；
- 原始仓库在哪里；
- 是否有许可证；
- 最近是否仍在维护；
- 问题和更新记录是否公开。

只有一个复制按钮、没有源码和维护记录的 Skill，不适合作为重要工作流的基础。

### 3. `SKILL.md` 能读懂吗

至少先看：

- `name` 和 `description` 是否与任务匹配；
- 主流程是否有清楚的输入、步骤、输出和检查；
- 是否要求忽略用户、系统或项目中的其他规则；
- 是否会读取与任务无关的文件或秘密；
- 是否把高风险动作藏在“准备工作”里。

如果主文件刻意不说明自己会做什么，不要因为下载量高就继续安装。

### 4. 还包含哪些文件

根据 [Agent Skills 规范](https://agentskills.io/specification)，Skill 除了 `SKILL.md`，还可能包含 `scripts/`、`references/` 和 `assets/`。

检查脚本使用什么语言、需要安装什么依赖、会访问哪些路径和网络地址。一个纯说明型 Skill 和一个会执行 Shell、下载程序、修改文件的 Skill，风险完全不同。

### 5. 它的权限与任务相称吗

整理 Markdown 不需要读取 SSH 密钥；生成本地报告通常也不需要自动发布到生产环境。

如果 Skill 需要写文件、访问网络、调用外部 App、部署、发消息或处理密钥，确认每项能力都能从任务目标中解释出来。

### 6. 有测试或可验证示例吗

示例不需要很复杂，但应该让你看到：

- 什么请求会触发；
- 需要什么输入；
- 结果如何验收；
- 缺少输入时会怎样；
- 哪些任务不应该使用它。

只有漂亮截图、没有可复现任务的 Skill，很难判断效果来自 Skill 还是演示者精心挑选的案例。

### 7. 它与现有 Skill 重叠吗

先列出已经安装的相邻 Skill。

如果两个 Skill 都声称负责“前端质量”“研究”“写作”或“发布”，需要判断谁是主负责人、谁只提供辅助能力。不能说清边界时，先只保留一个。

## 安装到哪个范围

Codex 可以从不同范围发现本地 Skill。当前官方文档列出的常见位置包括：

| 范围 | 适合放什么 | 常见位置 |
| --- | --- | --- |
| 项目 | 只适用于当前仓库的流程与约定 | 仓库内 `.agents/skills/` |
| 个人 | 多个项目都会使用的通用方法 | `~/.agents/skills/` |
| 管理员 | 组织统一提供的受控能力 | 管理员配置的位置 |
| 系统 | Codex 随产品提供的 Skill | 由 Codex 管理 |

判断方法很简单：

> 换一个完全不同的项目，它仍然应该存在吗？

- 如果答案是“不会”，放项目范围；
- 如果答案是“我所有项目都需要”，才考虑个人范围；
- 如果需要统一分发、连接器或管理能力，考虑由团队维护或打包成 Plugin。

不要为了省事，把所有项目规则都安装到个人目录。它们可能在另一个仓库错误触发。

## 安装以后先做四项验收

安装成功不等于已经可用。

### 1. 确认能被发现

重新加载客户端后，在 Skill 列表里检查名称和描述。找不到时不要重复安装，先看后面的[排错指南](/docs/skills/troubleshoot-skill)。

### 2. 显式调用

第一次先直接选择或提及 Skill，不测试自动触发。

给它一件 10 到 20 分钟就能判断结果的小任务，并使用非敏感材料。

### 3. 观察它实际做了什么

检查它是否：

- 只读取预期文件；
- 运行了说明中提到的脚本；
- 请求了合理权限；
- 访问了预期网站或 App；
- 在高风险动作前要求确认。

### 4. 对照交付物

回到最初的任务卡：输出是否真正解决问题？有没有证据？是否满足边界？

如果没有 Skill 的普通回答已经更好，或者为了一个简单任务引入大量依赖，就没有必要保留它。

## 更新、禁用和删除

Skill 不是安装一次就永远不用管。

建议维护一份很小的记录：

```text
名称：
来源：
安装范围：项目 / 个人 / 团队
当前版本或提交：
为什么保留：
最后一次验证：
涉及的脚本、网络和外部系统：
```

更新前先查看差异，尤其是 `SKILL.md`、`scripts/`、依赖和下载地址。不要把“全部自动更新”当成默认安全选择。

Codex 允许通过配置禁用本地 Skill，而不必立刻删除文件。适合下面这些情况：

- 暂时不需要，但以后可能恢复；
- 与另一个 Skill 发生重叠；
- 新版本需要重新审查；
- 正在排查它是否影响了触发结果。

长期不用、来源失效或无法解释其行为的 Skill，应从环境中移除。

## 一张可以直接使用的选择表

| 检查项 | 可以继续 | 应该暂停 |
| --- | --- | --- |
| 任务匹配 | 输入、流程和输出具体 | 只有宽泛宣传词 |
| 来源 | 作者、仓库、许可证可追踪 | 来源不明或只有复制命令 |
| 文件 | `SKILL.md` 和脚本可以检查 | 混淆、隐藏或远程下载未知内容 |
| 权限 | 与任务目标相称 | 索取无关文件、密钥或生产权限 |
| 维护 | 有版本、更新和问题记录 | 长期失联且依赖已经变化 |
| 验证 | 有小任务、示例或测试 | 只能相信截图和口号 |
| 重叠 | 与现有 Skill 分工清楚 | 多个 Skill 抢同一个任务 |

## 下一步

如果候选来自第三方，先继续阅读[第三方 Skill 安全吗？](/docs/skills/review-skill-security)，完成安装前审查。

如果已经选择好一个可信 Skill，就按照[第一次使用 Skill](/docs/skills/getting-started/use-first-skill)的流程，用真实小任务完成显式调用和结果检查。
