理解 Skill 的概念以后，最有效的下一步不是立刻写一个 `SKILL.md`。

而是先找一个现成 Skill，拿一项真实工作完整跑一遍。

这样你会亲眼看到三件事：

- Skill 是怎样进入一次任务的；
- 它改变的是一句回答，还是整套工作过程；
- 什么样的结果才算“这个 Skill 真的有用”。

这篇文章继续使用前文里的**运营周报**作为例子。你不需要先创建文件，也不需要理解所有目录规则。

完成以后，你应该能回答：

> 我怎样让 AI 明确使用某个 Skill，又怎样判断它不是只在普通聊天？

![稳定方法、本次目标和真实材料共同进入工作流程，再检查过程与结果](/images/docs/skills/use-first-skill-illustration.webp)

## 先完整做一次

第一次尝试 Skill 时，任务不要太大。

选择一件满足下面条件的工作：

- 你已经做过，知道正常结果是什么；
- 输入材料不涉及敏感信息；
- 20 分钟以内可以看出结果好坏；
- 最终有一个可以检查的交付物。

例如：

| 真实工作 | 可以借助的 Skill | 可以检查什么 |
| --- | --- | --- |
| 分析一份周运营数据 | 表格或数据分析 Skill | 是否检查数据、发现异常、给出依据 |
| 整理会议记录 | 文档 Skill | 是否区分结论、决定和待办 |
| 阅读一份行业报告 | PDF Skill | 是否引用了正确页面和原文依据 |
| Review 一个页面 | 前端或浏览器 Skill | 是否查看真实页面并给出可复现问题 |

不要第一次就要求 AI：

> 调研整个行业、生成完整战略、制作 PPT，再发给所有人。

任务越大，你越难判断问题到底出在 Skill、输入、工具，还是目标本身。

## 选择第一个 Skill

选择时先看三件事：

**它解决的任务是否足够具体？**

“帮助你提高效率”几乎无法判断适不适合。“读取并检查电子表格中的公式、数据和格式”就清楚得多。

**它需要什么输入？**

有的 Skill 只需要文字，有的需要文件、网页、仓库或外部 App。第一次使用，优先选择你已经准备好输入材料的 Skill。

**它可能执行什么动作？**

如果 Skill 会运行脚本、访问网络、修改文件或调用外部系统，先确认这些动作符合你的预期。来自陌生来源的 Skill 不要直接安装运行。

在 ChatGPT 或 Codex 的 Skill 选择器中，你通常可以先看到名称和描述。先用这两项判断它是否匹配任务；需要安装第三方 Skill 时，再进一步检查来源与文件内容。

这次示例假设你已经有一个可以处理表格的 Skill，并准备了一份本周运营数据。

## 先显式调用

第一次使用某个 Skill，优先采用**显式调用**。

在支持 Skill 选择器的界面中，直接选中它；在 Codex 中，也可以在提示词里写出 `$skill-name`。显式调用能减少“它到底有没有被选中”的不确定性。

例如：

```text
使用 $spreadsheets 分析我提供的本周运营数据。

目标：找出真正值得关注的变化，并生成一份运营周报。
重点检查：流量、转化率、客单价和广告投入。
输出：核心结论、异常、证据、可能原因、下周动作。
没有数据支持的原因必须标记为“假设”。
```

一条适合配合 Skill 使用的任务指令，通常仍然要说明四件事：

1. **目标**：这一次为什么要做；
2. **材料**：这一次处理什么数据或文件；
3. **重点**：你特别关心什么；
4. **交付物**：最终希望拿到什么。

Skill 保存的是长期方法，不会替你猜出本周日期、业务目标和特殊事件。

所以即使已经调用 Skill，也不要只写：

```text
帮我看看。
```

更完整的关系是：

```text
Skill：负责稳定的分析方法
Prompt：负责本次目标和材料
文件 / App：提供真实数据
```

## 检查是否真的有用

不要只问 AI：“你刚才使用 Skill 了吗？”

更可靠的办法是检查它有没有按预期完成工作。

### 1. 检查过程

如果这是一个运营分析 Skill，它是否：

- 先检查数据是否完整；
- 计算或核对了关键指标；
- 找出变化，而不只是复述所有数字；
- 把事实和推测分开；
- 在输出前做了必要的质量检查。

### 2. 检查证据

结论是否能回到原始材料？

例如“转化明显下降”后面，应该能看到具体时间范围、变化幅度或对应数据，而不是只有一个听起来专业的判断。

### 3. 检查交付物

结果是否符合你要求的结构？建议是否对应前面发现的问题？你能否直接拿它继续开会、写周报或做下一步判断？

可以用下面这张小表做第一次验收：

| 检查项 | 通过标准 |
| --- | --- |
| 输入理解 | 没有漏掉关键文件、字段和时间范围 |
| 工作过程 | 按这类任务应有的步骤完成，而不是直接生成答案 |
| 事实边界 | 数据、引用、事实和假设区分清楚 |
| 输出结构 | 符合约定格式，没有缺少关键部分 |
| 可执行性 | 下一步动作能对应到前面的发现 |

如果结果不理想，先判断是哪一层的问题：

- 本次目标没说清楚：修改 Prompt；
- Skill 的方法不适合：换一个 Skill；
- 输入材料不够：补充文件或上下文；
- Skill 方法正确但执行不稳定：记录下来，后面通过测试和迭代解决。

## 再测试自动触发

显式调用跑通以后，再尝试不写 Skill 名称，只描述任务：

```text
分析这份本周运营数据，找出流量、转化和广告投入中的异常，
区分事实与假设，并按“结论 / 证据 / 原因 / 动作”输出。
```

如果系统根据 Skill 的描述正确选择了它，这就是**隐式调用**或自动触发。

第一次测试不需要准备几十条 Prompt。先覆盖三种情况：

| 类型 | 测试 Prompt | 预期 |
| --- | --- | --- |
| 正常任务 | 分析本周运营数据并找异常 | 应该触发 |
| 输入不完整 | 帮我做周报，但没有提供数据 | 可以触发，但应先指出缺少输入 |
| 相似但不同 | 帮我写一封通知团队开周会的邮件 | 不应该触发运营分析 Skill |

第三种测试尤其重要。

一个 Skill 不是“触发得越多越好”。真正可靠的 Skill，既要在需要时出现，也要在不相关时保持沉默。

## 常见问题

### 找不到想用的 Skill

先确认当前产品和工作区是否已经提供它。Codex 本地 Skill 还可能来自个人目录、当前仓库或管理员配置；具体位置可以查阅[构建技能](/docs/build-skills#where-to-save-skills)。

如果需要从外部安装，不要只看名字和下载量。至少先确认作者、来源、`SKILL.md` 和附带脚本。

### 显式调用后结果仍然很普通

检查任务是否属于这个 Skill 的范围。调用一个写作 Skill，不代表它会自动理解你的业务指标；调用表格 Skill，也不代表它知道公司周报格式。

Skill 提供方法，本次业务背景仍然要由你提供。

### 自动触发时好时坏

这通常和 Skill 的 `description` 有关。描述可能太宽、太模糊，或者没有覆盖用户真实会说的话。

先保留刚才的三类测试 Prompt。后面的《怎样写好一个 Skill》会用它们改进触发边界。

### 结果看起来很好，但无法验证

把“好不好看”换成可检查的问题：

- 是否引用了真实输入？
- 是否完成了规定步骤？
- 是否满足输出格式？
- 是否把猜测写成事实？
- 是否存在明确遗漏？

到这里，你已经完成了第一次 Skill 使用闭环：

```text
选择合适的 Skill
→ 显式调用
→ 检查过程和结果
→ 尝试自动触发
→ 记录问题
```
