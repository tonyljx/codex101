上一页我们使用了一个现成 Skill。

现在开始创建属于自己的第一个 Skill。

这一步最容易犯的错误，是打开一个空白文件，然后努力想：

> “一个专业的 `SKILL.md` 应该写些什么？”

更好的起点是一项你已经做过的真实工作。

我们继续使用贯穿整个系列的例子：**运营周报**。

## 这次要做什么

最终要得到一个名为 `weekly-ops-review` 的 Skill。

每次收到一份新的运营数据，它都应该：

1. 检查输入是否完整；
2. 查看流量、转化率、客单价和广告投入；
3. 找出真正值得关注的变化；
4. 给出对应数据作为证据；
5. 区分事实和假设；
6. 输出核心结论、异常、原因和下周动作；
7. 在交付前完成一次 QA。

第一版先保持简单：

```text
weekly-ops-review/
└── SKILL.md
```

暂时不加脚本，不加十几份参考资料，也不追求覆盖所有运营场景。

一个能在真实任务中运行的简单 Skill，比一个看起来完整、从来没有测试过的 Skill 更有价值。

开始前准备三样东西：

- 一份可以测试的运营数据，必要时先去掉敏感字段；
- 一份你认为合格的历史周报；
- 你最近一次要求 AI 修改周报时给出的反馈。

这些真实材料比“请写得专业一些”更能说明你真正需要什么。

## 提取稳定方法

先不要写文件。

把一次真实工作拆成两类信息：**长期不变的方法**和**本次才会变化的任务材料**。

| 长期不变，适合放进 Skill | 每次变化，留给 Prompt 或文件 |
| --- | --- |
| 要检查哪些指标 | 本周实际数据 |
| 先检查输入，再分析异常 | 本周时间范围 |
| 事实和假设必须分开 | 本周活动与特殊事件 |
| 周报的固定输出结构 | 这次特别关注的问题 |
| 交付前的 QA 清单 | 临时需要补充的要求 |

如果把本周日期、某次活动名称和一次性目标都写进 Skill，它很快就会过期。

如果 Skill 里只有“深入分析数据”，它又没有保存任何真正的方法。

可以先用下面这段问题整理工作流：

```text
请分析我刚才完成这份运营周报的过程。

分别列出：
1. 每周都会重复的输入；
2. 稳定不变的工作步骤；
3. 中间需要做的判断；
4. 固定输出结构；
5. 交付前必须检查的事项；
6. 不应该猜测或自动执行的事情。

不要创建 Skill，先让我确认这套工作方法。
```

这一轮很重要。

你是在确认自己的 SOP，而不是让 AI 猜一套看起来合理的流程。

检查时重点删除两类内容：

- **常识性废话**：例如“保持专业”“确保高质量”；
- **不存在的流程**：例如你的周报从来不看库存，却被自动加入库存预测。

## 让 skill-creator 创建

方法确认以后，再让创建器生成 Skill。

在 Codex 中，可以显式调用内置的 `$skill-creator`。在支持通过聊天创建 Skill 的 ChatGPT 工作区里，也可以把相同的工作流说明交给创建流程。

下面是一段可以直接改写的创建请求：

```text
$skill-creator 创建一个名为 weekly-ops-review 的 Skill。

用途：收到周运营数据时，生成证据充分、事实与假设分开的运营周报。

触发场景：
- 用户要求分析周运营数据、周报、流量转化异常或广告表现；
- 输入通常是 CSV、Excel、表格内容或结构化数据。

不要触发：
- 只是在写周会通知、活动文案或普通邮件；
- 没有数据分析任务的泛泛总结。

工作流程：
1. 检查时间范围、字段和数据完整性；
2. 检查流量、转化率、客单价和广告投入；
3. 找出值得关注的变化并给出数据证据；
4. 区分事实、推断和仍需验证的问题；
5. 输出核心结论、异常、原因和下周动作；
6. 检查每个建议是否对应前面的发现。

第一版只使用 SKILL.md，不添加脚本。
创建后向我解释目录、description 和主要步骤，再给出 3 个测试任务。
```

这段请求没有直接替你写完整 `SKILL.md`。

它告诉创建器：

- Skill 要解决什么问题；
- 什么时候应该和不应该触发；
- 稳定的工作步骤是什么；
- 第一版的复杂度边界在哪里；
- 创建以后还要怎样验证。

如果创建器继续追问，优先给真实例子，不要只给形容词。

例如：

```text
不够具体：输出要深入、专业、有洞察。

更具体：先列出变化幅度最大的三个指标；
每个判断必须附对应数据；
证据不足的原因标记为“假设”；
每个下周动作必须对应一个已发现的问题。
```

## 检查生成结果

创建器生成文件后，不要立刻把它当作完成品。

先打开 Skill 目录，确认至少有：

```text
weekly-ops-review/
└── SKILL.md
```

一个基础 `SKILL.md` 分成两部分：

```markdown
---
name: weekly-ops-review
description: Analyze weekly operations data, identify evidence-backed anomalies, and produce an action-oriented weekly report. Use for weekly traffic, conversion, revenue, and ad performance reviews; do not use for meeting notices or general copywriting.
---

# Weekly Operations Review

...工作步骤、输出要求、QA 和边界...
```

现在只检查五件事。

### 名称是否清楚

`weekly-ops-review` 比 `helper`、`my-skill` 或 `data-pro` 更容易理解，也更方便以后查找。

### description 是否写了触发范围

description 不能只写“运营专家”。它至少要说明：

- 做什么；
- 什么任务应该使用；
- 哪些相似任务不属于它。

### 正文是否真的包含步骤

如果正文只是把 description 换一种说法，没有输入检查、判断顺序、输出格式和 QA，它仍然只是一段介绍。

### 是否混入一次性材料

检查有没有本周日期、具体活动或只属于某一家公司的临时信息。

### 是否过度设计

第一版不需要为每个指标创建一个脚本，也不需要把所有运营知识塞进一个文件。

如果生成结果太大，可以明确要求：

```text
请把第一版缩小到“周运营数据检查与周报输出”这一项工作，
删除没有实际改变执行方式的说明，暂时不要增加脚本和额外目录。
```

Skill 在 Codex 中的实际保存位置可能属于当前目录、仓库、个人或管理员范围。需要确认作用范围时，查看[技能的保存位置](/docs/build-skills#where-to-save-skills)。

## 完成第一次运行

先显式调用刚创建的 Skill：

```text
使用 $weekly-ops-review 分析我提供的本周运营数据。

时间范围：8 月 1 日到 8 月 7 日。
本周重点：广告投入增加后，转化率为什么没有同步提升。
输出一份可以直接用于周会的运营周报。
```

第一次运行不要只看文风。

逐项确认：

- 是否先检查了输入；
- 是否遗漏关键指标；
- 是否给每个重要结论提供证据；
- 是否把无法确认的原因标成假设；
- 是否按固定结构输出；
- 是否让动作对应前面的发现。

如果输入缺少必要字段，好的结果不应该编造数据继续完成，而应该明确告诉你缺少什么、还能完成哪一部分。

保存第一次运行的 Prompt、输入和结果。

它们会成为后续测试的基线。

## 只改进一个问题

第一次测试几乎一定会发现问题。

先只选择影响最大的一个。

例如结果列出了异常，但没有按照影响排序。不要同时重写整个 Skill，可以补一条明确规则：

```text
完成异常识别后，按“业务影响 × 证据强度”排序，
最多保留五项；无法量化影响时说明判断依据。
```

然后用同一个任务重新运行。

这样你才能判断这次修改是否真的带来了变化。

一个简单而有效的迭代记录可以是：

| 版本 | 发现的问题 | 修改 | 结果 |
| --- | --- | --- | --- |
| v0.1 | 异常没有优先级 | 增加影响与证据排序 | 前三项更聚焦 |
| v0.2 | 输入缺失时仍继续推测 | 增加输入检查和停止条件 | 会先列出缺失字段 |

不要一开始追求精确版本系统。先保留“为什么改、改了什么、是否有效”这三项事实。

## 完成标准

第一个 Skill 不需要完美。

达到下面这些条件，就可以进入下一篇：

- 已经从一项真实工作中提取稳定方法；
- 已经生成一个可以读取的 `SKILL.md`；
- name 和 description 能说明用途与边界；
- 已经使用真实输入显式运行至少一次；
- 已经根据结果完成一次小修改；
- 保留了第一次测试的 Prompt、输入和输出。

到这里，你已经走完了最小创建闭环：

```text
真实工作
→ 提取稳定方法
→ 创建 Skill
→ 检查文件
→ 用真实任务运行
→ 根据证据修改一次
```

下一篇我们会打开这个 Skill，系统处理三个更难的问题：description 怎样写、内容应该放在哪个文件，以及如何避免 `SKILL.md` 越写越长。
