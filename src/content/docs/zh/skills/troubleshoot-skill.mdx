Skill “没有工作”可能代表完全不同的问题：

- 列表里根本看不到；
- 可以看到，但显式调用失败；
- 显式调用正常，自动触发却不稳定；
- 触发了另一个相似 Skill；
- 已经触发，但没有读取支持文件；
- 流程执行了，结果仍然很普通；
- 在一个项目可用，换到另一个项目就消失。

如果把这些现象都归结为“Prompt 不够好”，你会不断修改错误的位置。

更有效的方法是把一次 Skill 运行看成五道门：

```text
发现：客户端能不能看见
→ 路由：任务会不会选择它
→ 加载：主文件和支持资料能不能打开
→ 执行：输入、权限、脚本和工具是否可用
→ 输出：流程是否真的改善结果
```

先找到失败发生在哪一道门，再修改对应层。

![Skill 从发现、路由、加载、执行到输出的五层排错漏斗，每层对应不同检查](/images/docs/skills/troubleshoot-skill-illustration.webp)

## 第一步：把故障变小

不要用一个包含十个步骤的大任务排错。

准备一个最小测试：

```text
Skill：weekly-ops-review
任务：读取一份不含敏感数据的小型 CSV
预期：检查字段，并输出三项最值得关注的变化
禁止：不访问外部 App，不修改源文件
```

同时记录：

- 当前客户端和项目目录；
- Skill 的实际路径；
- 这次是显式调用还是自动触发；
- 完整错误或不符合预期的现象；
- 最近修改了什么。

最小任务的目标不是证明 Skill 很强，而是让每一层都容易观察。

## 第一层：客户端能发现它吗

先打开 Skill 列表或选择器。

### 列表里完全没有

优先检查：

1. 文件夹里是否真的有 `SKILL.md`；
2. 文件名大小写是否正确；
3. YAML frontmatter 是否可以解析；
4. `name` 和 `description` 是否存在；
5. Skill 是否放在当前客户端支持的位置；
6. 当前项目目录是否属于预期仓库；
7. Skill 是否被配置为禁用；
8. 客户端是否需要重新加载或重启。

根据当前 [OpenAI 构建技能文档](https://developers.openai.com/codex/build-skills)，Codex 会从项目、用户、管理员和系统范围发现 Skill。常见项目位置是仓库内 `.agents/skills/`，个人位置是 `~/.agents/skills/`。

一个项目 Skill 换到另一个无关目录后消失，可能是正确行为，而不是故障。

### 列表里出现两个同名 Skill

Codex 不会自动把同名 Skill 合并成一份。

记录两份 Skill 的完整路径，暂时禁用或改名其中一份，再运行最小测试。不要只凭名称猜自己调用的是哪一个。

### Skill 太多，某些没有出现

Codex 会先把 Skill 的名称和描述放进可发现目录，并限制它们占用的上下文。安装非常大的目录时，部分描述可能被缩短，极端情况下可能有 Skill 被省略并显示警告。

处理方法不是继续增加一个“总路由 Skill”，而是先：

- 禁用长期不用的 Skill；
- 删除重复和过宽的 Skill；
- 把项目专用能力留在项目范围；
- 保持每个 Skill 只负责一个清楚任务。

## 第二层：显式调用能运行吗

自动触发不稳定时，先显式调用。

在支持选择器的界面直接选中 Skill；在 Codex CLI 或 IDE 中，可以通过 `/skills` 或输入 `$` 找到并提及它。

### 显式调用也失败

问题通常不在 description 的“触发文案”，优先检查：

- `SKILL.md` 能否读取；
- 主文件里的路径是否存在；
- 依赖是否安装；
- 脚本是否能在当前系统运行；
- 当前目录是否正确；
- 输入文件是否存在；
- 所需工具或 App 是否可用；
- 权限是否被拒绝。

### 显式调用正常

这证明 Skill 的主体至少可以工作。接下来再检查自动路由，而不是重写整个目录。

可以保留两条结果：

| 测试 | 结果 | 说明 |
| --- | --- | --- |
| 显式调用 | 正常 | 主文件、基本执行路径可用 |
| 自动触发 | 未触发 | 优先检查 description、任务表达和重叠 |

## 第三层：自动触发为什么失败

自动触发主要依赖 Skill 的名称和 description 判断任务是否匹配。

系统在决定使用之前，通常还没有读取完整 `SKILL.md`。所以把更多触发词堆进正文，往往不会解决问题。

### description 太宽

```yaml
description: Use for data, reports, analysis, writing, research, and business tasks.
```

它看似覆盖很多任务，实际上没有告诉系统何时应该选它，也容易与其他 Skill 重叠。

### description 太窄

```yaml
description: Use when the user says "生成周运营报告".
```

真实用户可能会说“流量涨了但订单没涨，帮我查原因”，没有使用固定句子。

### 更好的写法

```yaml
description: >-
  Use for weekly operations reviews, period-over-period metric comparisons,
  and traffic, conversion, revenue, or advertising anomaly analysis.
  Do not use for meeting summaries, marketing copy, or general metric definitions.
```

它同时说明：

- 核心任务；
- 用户可能使用的真实表达；
- 输入或分析类型；
- 最容易混淆的相邻边界。

### 用三组 Prompt 验证

| 类型 | 示例 | 预期 |
| --- | --- | --- |
| 应触发 | 比较本周与上周转化，找出异常 | 触发 |
| 换一种说法 | 流量涨了但订单没涨，帮我查原因 | 触发 |
| 相邻任务 | 把这份已经写好的周报改短 | 不触发 |

如果第一条触发、第二条不触发，description 可能只覆盖了标准术语；如果第三条也触发，范围可能太宽。

## 第四层：是不是被相似 Skill 抢走了

当两个 Skill 都能解释同一个任务时，路由很难稳定。

例如：

- `content-writing` 和 `seo-article`；
- `frontend-design` 和 `ui-polish`；
- `data-analysis` 和 `weekly-ops-review`；
- `github-workflow` 和 `fix-ci`。

不要只在 description 里互相添加更多关键词。先定义所有权：

| Skill | 主负责 | 不负责 |
| --- | --- | --- |
| `weekly-ops-review` | 从业务数据发现周度异常并形成复盘 | 编辑已有周报措辞 |
| `writing-editor` | 改写、压缩和统一现有文本 | 重新计算运营指标 |

还可以选择：

- 合并实际上属于同一任务的 Skill；
- 把一个过宽 Skill 拆成更具体的能力；
- 禁用当前项目不需要的候选；
- 第一次关键任务直接显式指定负责人。

大型目录的重点不是给每个 Skill 排一个永久优先级，而是减少语义重叠，让每项能力的所有权可以解释。

## 第五层：支持文件为什么没有读取

Skill 已经触发，却表现得像没有看到 `references/` 或 `assets/`，常见原因是主文件没有写清楚读取条件。

不要只写：

```text
更多信息在 references 里。
```

改成可以执行的路由：

```text
当任务涉及周报指标定义时，读取 references/metrics.md。
生成管理层版本前，读取 references/executive-format.md。
需要创建交付文件时，复制 assets/weekly-report-template.md。
```

继续检查：

- 路径是否相对于 Skill 根目录；
- 文件名和大小写是否一致；
- 文件是否真的随 Skill 一起安装；
- 内容是否移动或重命名后留下旧链接；
- 当前客户端是否支持相关脚本语言和工具。

渐进式加载的目的不是“Agent 会自动猜到所有资料”，而是让 `SKILL.md` 明确告诉它什么时候需要哪一份支持内容。

## 第六层：脚本、输入和权限

显式调用成功进入流程后，仍可能在执行阶段失败。

### 缺少输入

Skill 应该列出缺少什么，而不是继续猜测。

```text
已提供：本周 CSV
缺少：上周 CSV、指标时区
无法完成：环比计算
可以先做：字段检查和本周异常扫描
```

### 脚本失败

记录完整错误，然后检查：

- 运行时是否存在；
- 版本是否兼容；
- 依赖是否安装；
- 文件路径是否适用于当前系统；
- 工作目录是否正确；
- 输入编码和格式是否符合预期。

不要把错误信息删掉后只对 Agent 说“再试一次”。完整错误通常比重新描述任务更有用。

### 权限被拒绝

先确认权限是否真的必要。

如果任务合理需要访问文件、网络或 App，再按照客户端提示授权；如果一个简单整理任务要求读取整个主目录或生产账户，应该回到安全审查，而不是为了让它运行就全部放开。

## 第七层：触发了，但结果仍然不好

这时问题已经从“触发故障”进入“输出质量”。

优先检查：

- 流程是否规定了输入检查；
- 步骤是否只有口号，没有可执行动作；
- 输出契约是否明确；
- QA 是否能观察；
- 事实、假设和建议是否分开；
- 固定计算是否需要确定性脚本；
- 本次 Prompt 是否提供了目标和材料。

继续使用[怎样测试 Skill](/docs/skills/authoring/test-and-iterate)里的基线、断言和回归测试，不要再修改 description 来解决已经触发后的质量问题。

## 一张故障对照表

| 现象 | 最可能层级 | 第一检查点 |
| --- | --- | --- |
| 列表里没有 | 发现 | 路径、文件名、frontmatter、禁用状态 |
| 出现两个同名项 | 发现 | 完整路径与作用域 |
| 显式调用失败 | 加载 / 执行 | 文件路径、依赖、输入、权限 |
| 显式正常，自动不触发 | 路由 | description 与真实表达 |
| 经常触发错误 Skill | 路由 | 相邻 Skill 的所有权边界 |
| 不读取 references | 加载 | 主文件是否写明读取条件和路径 |
| 脚本在另一台机器失败 | 执行 | 运行时、系统、路径和依赖兼容性 |
| 已触发但结果普通 | 输出 | 流程、输出契约、QA 和本次材料 |

## 最小排错顺序

每次只按下面顺序前进：

```text
1. 列表里能看到吗？
2. 显式调用能完成最小任务吗？
3. 自动触发能识别不同说法吗？
4. 相邻 Skill 会不会抢任务？
5. 支持文件和脚本能按需读取吗？
6. 输入、权限和环境是否满足？
7. 最终结果是否通过质量断言？
```

修复一层后，重新运行同一个最小任务，再继续下一层。这样你会得到一条可以解释的因果链，而不是改了十个地方后碰巧成功一次。

如果问题来自多个 Skill 的重叠或分工，下一篇继续看[多个 Skill 怎么配合？](/docs/skills/compose-multiple-skills)。
