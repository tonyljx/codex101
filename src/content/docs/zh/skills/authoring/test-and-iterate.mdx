Skill 创建完成以后，最常见的验收方式是：

> 随便试一句，看起来还不错，就算完成。

这种测试只能证明它在某一次任务里没有立刻失败。

它不能回答：

- 用户换一种说法，它还会不会触发；
- 输入不完整时，它会不会开始编造；
- 相似但不相关的任务，会不会误触发；
- 有 Skill 的结果，是否真的比没有 Skill 更好；
- 修改一条规则后，旧任务会不会退化。

一个 Skill 要进入长期使用，至少需要一套小而真实的测试集。

这篇会为 `weekly-ops-review` 建立第一版评估记录。

![应该触发、不应触发和异常输入分别进入触发准确性、输出质量与回归测试流程](/images/docs/skills/test-and-iterate-illustration.webp)

## 分开测试两件事

Skill 测试包含两个不同问题。

### 触发准确性

系统是否在正确的时候选择了 Skill？

这里既要测试：

- **应该触发**：真正属于运营数据分析的任务；
- **不应触发**：用词相似，但任务目标不同的请求。

### 输出质量

Skill 被选中以后，是否按照预期完成了工作？

例如：

- 有没有检查输入；
- 有没有找到真正的异常；
- 有没有给出证据；
- 有没有把事实和推测分开；
- 有没有遵守输出契约；
- 有没有完成 QA。

这两类问题不能混在一起。

如果 Skill 根本没有触发，应该先修改 description 或调用方式；如果已经触发但结果仍然不好，问题更可能在正文、支持材料、输入或脚本。

## 建立测试集

第一版不需要复杂评测平台。

用 8 到 12 条真实 Prompt，就能发现大部分明显问题。

### 应该触发

不要只准备几句几乎相同的话。覆盖用户可能采用的不同表达：

| 编号 | 测试任务 | 特别检查 |
| --- | --- | --- |
| P1 | 分析这周运营数据，帮我找异常 | 泛化表达是否能匹配 |
| P2 | 本周流量涨了，但订单没涨，帮我查原因 | 没有出现“周报”时是否匹配 |
| P3 | 根据 CSV 做一份周运营复盘 | 文件型输入是否匹配 |
| P4 | 比较本周和上周的转化率、客单价和广告回报 | 指标型表达是否匹配 |
| P5 | 给管理层准备一页运营周报，事实和猜测分开 | 交付物表达是否匹配 |

### 不应该触发

负例不要写成完全无关的问题。应该选择最容易混淆的相邻任务：

| 编号 | 测试任务 | 为什么不应触发 |
| --- | --- | --- |
| N1 | 帮我写一封通知团队开运营周会的邮件 | 是写作，不是数据分析 |
| N2 | 想十个下周促销活动标题 | 是创意生成 |
| N3 | 总结这段运营会议记录 | 是会议纪要整理 |
| N4 | 解释什么是转化率 | 是概念解释 |
| N5 | 把这份已经写好的周报改得更简洁 | 是编辑，不是周报分析 |

### 输入异常

输出质量还要覆盖不理想输入：

- 没有时间范围；
- 缺少上周数据，却要求计算环比；
- 字段名称不一致；
- 数据里出现空值或明显错误；
- 用户要求直接给原因，但证据不足。

测试集的目标不是为难 Skill，而是模拟真实工作。

如果生产环境经常收到缺字段的表格，测试里只有完美 CSV，就无法预测真正的表现。

## 先记录基线

在评估 Skill 之前，选择三项代表性任务，先在**不使用 Skill**的情况下运行一次。

保留：

- 原始 Prompt；
- 输入文件或输入摘要；
- 完整输出；
- 使用时间；
- 你发现的主要问题。

然后在相同条件下显式调用 Skill，再运行一次。

比较时不要只问“哪一份读起来更好”。

使用同一组检查项：

| 维度 | 没有 Skill | 使用 Skill |
| --- | --- | --- |
| 是否检查输入 |  |  |
| 是否找出关键异常 |  |  |
| 结论是否有数据依据 |  |  |
| 是否区分事实与假设 |  |  |
| 是否符合输出契约 |  |  |
| 建议是否对应发现 |  |  |
| 是否出现明显错误 |  |  |

如果使用 Skill 后只是标题更整齐，核心判断没有改善，就不能说它已经有效。

基线还有另一个作用：防止把模型本来就会做的事情误认为 Skill 的贡献。

## 运行并记录结果

### 先测触发，再测质量

建议按这个顺序：

```text
1. 不写 Skill 名称，运行应该触发的 Prompt
2. 记录是否触发
3. 运行不应该触发的 Prompt
4. 记录是否误触发
5. 显式调用 Skill，运行输出质量测试
6. 保存完整结果和失败现象
```

触发判断存在一定波动时，同一条 Prompt 可以重复运行三次，记录成功次数。

例如：

| Prompt | 第 1 次 | 第 2 次 | 第 3 次 | 结论 |
| --- | --- | --- | --- | --- |
| P2 | 触发 | 未触发 | 触发 | description 对异常分析表达覆盖不足 |
| N5 | 未触发 | 未触发 | 未触发 | 边界稳定 |

不要因为一次成功就忽略另外两次失败。

也不要只保存一个“通过 / 不通过”。完整输出能帮助你判断问题究竟发生在哪一步。

可以先使用一个简单记录表：

| 测试 ID | 是否触发 | 输出检查 | 主要失败 | 下一步 |
| --- | --- | --- | --- | --- |
| P1 | 是 | 4/6 | 没有检查时间范围 | 修改输入检查 |
| P2 | 不稳定 | — | 两次只识别为普通问答 | 修改 description |
| N5 | 否 | — | 无 | 保留 |

## 用断言检查输出

“这份周报够不够好”容易变成主观争论。

断言是对结果提出一个可以检查的具体要求。

运营周报 Skill 可以先有这些断言：

```text
A1. 输出明确写出分析使用的时间范围。
A2. 至少覆盖流量、转化率、客单价和广告投入中实际存在的字段。
A3. 每项核心异常都包含对应数值或来源位置。
A4. 证据不足的原因被标记为假设或待验证。
A5. 每个建议至少对应一项前文发现。
A6. 输入缺少关键字段时，不编造环比结果。
A7. 最终输出包含结论、异常、原因和动作四部分。
```

好的断言应该：

- 能从最终输出或执行记录中观察；
- 对真实质量有意义；
- 不把措辞差异误判成失败；
- 不要求模型输出只有一种正确句子。

例如“必须使用‘显著下滑’四个字”不是好的质量断言。“必须给出变化幅度和对应时间范围”更有意义。

断言也不能只检查格式。

一份报告可能标题齐全，却把错误数据写得非常整齐。至少要同时覆盖：

- 内容正确性；
- 证据完整性；
- 工作流程；
- 输出结构；
- 安全与边界。

## 从失败定位问题

测试失败后，不要立刻重写整个 Skill。

先根据现象定位最可能的层级。

| 失败现象 | 优先检查 |
| --- | --- |
| 应该触发但没有触发 | description 是否覆盖真实表达，范围是否太窄 |
| 不相关任务经常误触发 | description 是否过宽，是否缺少相邻边界 |
| 已触发但跳过关键步骤 | `SKILL.md` 的顺序、检查点和输出契约 |
| 不知道该读取哪份资料 | 主文件是否写清文件路径、读取条件和用途 |
| 同一计算反复出错 | 是否应该增加确定性脚本或校验 |
| 输入缺失时继续猜测 | Required inputs、停止条件和错误恢复规则 |
| 输出很长但没有重点 | 优先级规则、数量限制和交付物受众 |

### 不触发：先改描述，不要堆正文

系统还没打开 `SKILL.md` 时，正文写得再详细也解决不了选择问题。

### 已触发但做错：检查流程

如果 Skill 已经被显式调用，仍然漏掉输入检查，问题通常不在 description。检查正文是否只是说“检查数据”，却没有规定检查什么、缺失时怎么办。

### 结果不稳定：找需要确定性的步骤

并不是所有波动都要用脚本解决。

先看能否通过更明确的输入、判断和输出规则改善。只有固定计算、格式验证或数据转换确实需要可重复结果时，再加入脚本。

## 根据证据迭代

一次只修改一个主要问题，然后重新运行相关测试和少量回归测试。

例如 P2 经常不触发：

```text
问题：用户说“流量涨了但订单没涨”时没有选择 Skill。

修改前：
Use for weekly operations reports.

修改后：
Use for weekly metric reviews, traffic or conversion anomaly analysis,
and questions about why operational metrics changed across periods.
```

修改后至少重新运行：

- P2：确认目标表达更容易触发；
- P1：确认原来的典型任务没有退化；
- N4：确认“解释转化率”没有被新关键词误触发。

这就是最小回归测试。

维护一张简短迭代表：

| 版本 | 修改原因 | 改动位置 | 影响测试 | 结果 |
| --- | --- | --- | --- | --- |
| v0.1 | P2 触发不稳定 | description | P1、P2、N4 | P2 改善，N4 未误触发 |
| v0.2 | 缺字段时仍推测 | Required inputs | E1、P1 | 会先列缺失项 |

不要为了让一个测试通过，加入只针对那一句话的特殊规则。

如果修改后只会识别测试集里的固定措辞，却无法处理真实用户的其他表达，这就是过拟合。持续加入新近出现的真实任务，并保留一部分没有参与修改的验证 Prompt。

![从建立真实测试集、记录无 Skill 基线到定位失败并单点回归的六步漫画](/images/docs/skills/test-and-iterate-comic.webp)

## 什么时候算完成

Skill 很少有永远不再修改的一天。

但达到下面这些标准后，它可以进入日常试用：

- 有一组来源于真实工作的应触发 Prompt；
- 有一组相邻但不应触发的负例；
- 覆盖正常输入和至少两类异常输入；
- 已经比较过有 Skill 与无 Skill 的基线；
- 输出质量有可以观察的断言；
- 主要失败能够定位到 description、正文、支持材料或脚本；
- 每次修改都会运行相关测试和最小回归测试；
- 已知限制已经记录，不把未验证能力写成承诺。

完整闭环是：

```text
真实任务
→ 建立正例、负例和异常输入
→ 记录无 Skill 基线
→ 测试触发和输出
→ 用断言定位失败
→ 一次修改一个问题
→ 回归测试
→ 把新失败加入测试集
```

做到这里，你拥有的已经不只是一个 `SKILL.md` 文件。

你开始拥有一项可以解释、验证和持续改进的 AI 工作能力。
