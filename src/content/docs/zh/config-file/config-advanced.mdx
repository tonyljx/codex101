当你需要更细粒度地控制提供方、策略和集成时，请使用这些配置项。若你只需要快速入门，先看 [配置基础](/docs/config-file/config-basic)。

如果你想了解项目指导、可复用能力、自定义斜杠命令、子智能体工作流和集成能力的背景概念，参见 [自定义](/docs/customization/overview)。如果你想查具体键名，参见 [配置参考](/docs/config-file/config-reference)。

## 配置档案

配置档案允许你保存具名配置层，并从 CLI 中切换。传入 `--profile profile-name` 时，Codex 会先加载 `~/.codex/config.toml`，再叠加 `~/.codex/profile-name.config.toml`。配置档案名称可以包含字母、数字、连字符和下划线。

每个配置档案都使用独立 TOML 文件。配置档案文件中直接写顶层配置键，不要嵌套在 `[profiles.profile-name]` 下面。

<CodeBlock code={"# ~/.codex/deep-review.config.toml\nmodel = \"gpt-5.5\"\nmodel_reasoning_effort = \"xhigh\"\napproval_policy = \"on-request\"\nmodel_catalog_json = \"/Users/me/.codex/model-catalogs/deep-review.json\""} language="toml" />

<CodeBlock code={"codex --profile deep-review\ncodex exec --profile deep-review \"review this change\""} language="bash" />

由于配置档案文件是叠加在用户基础配置之上、项目和 CLI 配置之下的一层，它只需要写出和基础配置不同的值。配置档案文件也可以覆盖 `model_catalog_json`；如果两个文件都设置了该值，Codex 会使用配置档案中的值。

从 Codex 0.134.0 开始，`--profile` 不再读取 `config.toml` 中的 `[profiles.profile-name]`，顶层的 `profile = "profile-name"` 选择器也不再支持。请把旧配置档案设置移动到 `~/.codex/profile-name.config.toml`，然后从 `config.toml` 中移除对应的 `[profiles.profile-name]` 表和 `profile = "profile-name"` 选择器。

## 通过 CLI 做一次性覆盖

除了直接编辑 `~/.codex/config.toml` 之外，你还可以在 CLI 中只对单次运行做配置覆盖：

-   优先使用专用 flag，例如 `--model`
-   当你需要覆盖任意配置键时，使用 `-c` / `--config`

示例：

<CodeBlock code={"# 专用 flag\ncodex --model gpt-5.6-terra\n\n# 通用键值覆盖（这里的值是 TOML，不是 JSON）\ncodex --config model='\"gpt-5.6-terra\"'\ncodex --config sandbox_workspace_write.network_access=true\ncodex --config 'shell_environment_policy.include_only=[\"PATH\",\"HOME\"]'"} language="bash" />

补充说明：

-   `--config` 里的值使用的是 TOML 语法，而不是 JSON。
-   你可以覆盖嵌套键，例如 `mcp_servers.context7.enabled=false`。
-   如果拿不准，请给值加上引号，避免 shell 因为空格把它拆开。
-   如果某个值无法被解析成 TOML，Codex 会把它当作普通字符串处理。

## 配置与状态文件位置

Codex 会把本地状态保存在 `CODEX_HOME` 下，默认路径是 `~/.codex`。

你在其中最常见到的文件包括：

-   `config.toml`（你的本地配置）
-   `auth.json`（如果你使用基于文件的凭据存储；否则会使用操作系统的 keychain / keyring）
-   `history.jsonl`（如果启用了历史记录持久化）
-   其他按用户保存的状态，例如日志与缓存文件

关于认证细节，包括凭据存储模式，参见 [认证](/docs/auth)。关于完整配置键列表，参见 [配置参考](/docs/config-file/config-reference)。

关于被提交到仓库或系统路径中的共享默认配置、规则和技能，参见 [Team Config](/docs/enterprise/admin-setup#step-4-standardize-local-configuration-with-team-config)。

如果你只是想让内建的 OpenAI 提供方指向某个 LLM 代理、路由器，或启用了数据驻留的项目，可以直接在 `config.toml` 中设置 `openai_base_url`，而不必定义一个新的提供方。这样会修改内建 `openai` 提供方的基础 URL，而不需要额外创建 `model_providers.<id>` 条目。

<CodeBlock code={"openai_base_url = \"https://us.api.openai.com/v1\""} language="toml" />

## 项目配置文件（.codex/config.toml）

除了用户级配置外，Codex 还会读取仓库内 `.codex/config.toml` 里的项目级覆盖配置。Codex 会从项目根目录一路向下遍历到当前工作目录，并加载沿途找到的所有 `.codex/config.toml`。如果多个文件定义了同一个键，则离当前工作目录最近的文件生效。

出于安全考虑，Codex 只会在项目被标记为可信时加载这些项目级配置文件。如果项目不可信，Codex 会忽略项目中的 `.codex/` 配置层，包括 `.codex/config.toml`、项目本地钩子和项目本地规则。用户层和系统层保持独立，仍会正常加载。

项目配置中的相对路径，例如 `model_instructions_file`，会相对于包含该 `config.toml` 的 `.codex/` 目录来解析。

项目配置文件不能覆盖可能重定向凭据、改变宿主应用请求元数据、改变提供方认证、选择配置档案，或运行本机通知与遥测命令的设置。Codex 会忽略项目本地 `.codex/config.toml` 中的下列键，并在启动时打印警告：`openai_base_url`、`chatgpt_base_url`、`apps_mcp_product_sku`、`model_provider`、`model_providers`、`notify`、`profile`、`profiles`、`experimental_realtime_ws_base_url` 和 `otel`。提供方、通知和遥测相关键应设置在用户级 `~/.codex/config.toml` 中；配置档案请通过 `--profile profile-name` 和 `~/.codex/profile-name.config.toml` 选择。

## 生命周期钩子

Codex 还可以加载位于活动配置层旁边的生命周期钩子，来源可以是 `hooks.json` 文件，也可以是 `config.toml` 文件中的内联 `[hooks]` 表。

实践中最常用的四个位置是：

-   `~/.codex/hooks.json`
-   `~/.codex/config.toml`
-   `<repo>/.codex/hooks.json`
-   `<repo>/.codex/config.toml`

项目本地钩子只会在项目 `.codex/` 配置层受信任时加载。用户级钩子与项目信任状态无关。

内联 TOML 钩子使用与 `hooks.json` 相同的事件结构：

<CodeBlock code={"[[hooks.PreToolUse]]\nmatcher = \"^Bash$\"\n\n[[hooks.PreToolUse.hooks]]\ntype = \"command\"\ncommand = '/usr/bin/python3 \"$(git rev-parse --show-toplevel)/.codex/hooks/pre_tool_use_policy.py\"'\ntimeout = 30\nstatusMessage = \"Checking Bash command\""} language="toml" />

如果同一配置层同时包含 `hooks.json` 和内联 `[hooks]`，Codex 会同时加载并给出警告。建议每个配置层只使用其中一种表示方式。

关于当前支持的事件列表、输入字段、输出行为和限制，请参见 [Hooks](/docs/hooks)。

关于子智能体角色配置，也就是 `config.toml` 中的 `[agents]`，参见 [子智能体](/docs/agent-configuration/subagents)。

## 项目根目录检测

Codex 会从当前工作目录向上查找项目根，从而发现项目配置，例如 `.codex/` 配置层和 `AGENTS.md`。

默认情况下，Codex 会把包含 `.git` 的目录视为项目根。若要自定义这一行为，可以在 `config.toml` 中设置 `project_root_markers`：

<CodeBlock code={"# 当目录中包含以下任一标记时，将其视为项目根目录。\nproject_root_markers = [\".git\", \".hg\", \".sl\"]"} language="toml" />

如果你设置 `project_root_markers = []`，Codex 就不会再向父目录搜索，而是直接把当前工作目录视为项目根。

## 自定义模型提供方

模型提供方定义了 Codex 如何连接到某个模型，例如基础 URL、`wire_api` 协议、认证方式，以及可选的 HTTP 请求头。自定义提供方不能复用内建的保留 ID：`openai`、`ollama` 和 `lmstudio`。

你可以定义额外的提供方，并让 `model_provider` 指向它们：

<CodeBlock code={"model = \"gpt-5.6-terra\"\nmodel_provider = \"proxy\"\n\n[model_providers.proxy]\nname = \"OpenAI using LLM proxy\"\nbase_url = \"http://proxy.example.com\"\nenv_key = \"OPENAI_API_KEY\"\n\n[model_providers.local_ollama]\nname = \"Ollama\"\nbase_url = \"http://localhost:11434/v1\"\n\n[model_providers.mistral]\nname = \"Mistral\"\nbase_url = \"https://api.mistral.ai/v1\"\nenv_key = \"MISTRAL_API_KEY\""} language="toml" />

如果自定义提供方支持独立的 Web search endpoint，请在提供方配置中声明该能力：

<CodeBlock code={"[model_providers.proxy]\nname = \"OpenAI using LLM proxy\"\nbase_url = \"https://proxy.example.com/v1\"\nenv_key = \"OPENAI_API_KEY\"\nsupports_standalone_web_search = true"} language="toml" />

自定义提供方的该设置默认为 `false`。独立 Web search 仍在开发中，且默认关闭。把提供方能力设为 `true` 并不会自行启用它：提供方必须支持兼容 endpoint，所选模型和运行时也必须支持独立搜索。配置的 [`web_search` 模式](/docs/web-search)和托管搜索限制仍然适用。

如有需要，也可以添加请求头：

<CodeBlock code={"[model_providers.example]\nhttp_headers = { \"X-Example-Header\" = \"example-value\" }\nenv_http_headers = { \"X-Example-Features\" = \"EXAMPLE_FEATURES\" }"} language="toml" />

如果某个提供方需要 Codex 通过外部凭据助手获取 bearer token，可以使用命令式认证：

<CodeBlock code={"[model_providers.proxy]\nname = \"OpenAI using LLM proxy\"\nbase_url = \"https://proxy.example.com/v1\"\nwire_api = \"responses\"\n\n[model_providers.proxy.auth]\ncommand = \"/usr/local/bin/fetch-codex-token\"\nargs = [\"--audience\", \"codex\"]\ntimeout_ms = 5000\nrefresh_interval_ms = 300000"} language="toml" />

认证命令不会收到 `stdin`，并且必须把 token 输出到 `stdout`。Codex 会去掉首尾空白，把空 token 视为错误，并按 `refresh_interval_ms` 主动刷新；设置 `refresh_interval_ms = 0` 后，只会在认证重试后刷新。不要把 `[model_providers.<id>.auth]` 与 `env_key`、`experimental_bearer_token` 或 `requires_openai_auth` 混用。

### Amazon Bedrock 提供方

Codex 内建了 `amazon-bedrock` 模型提供方。可以直接把它设为 `model_provider`；和自定义提供方不同，这个内建提供方只支持嵌套的 AWS 配置档案和区域覆盖项。

<CodeBlock code={"model_provider = \"amazon-bedrock\"\nmodel = \"<bedrock-model-id>\"\n\n[model_providers.amazon-bedrock.aws]\nprofile = \"default\"\nregion = \"eu-central-1\""} language="toml" />

如果省略 `profile`，Codex 会使用标准 AWS 凭据链。请把 `region` 设为处理请求的受支持 Bedrock 区域。

关于完整设置流程、认证选项、受支持模型和功能可用性，请参见[通过 Amazon Bedrock 使用 ChatGPT Work 和 Codex](/docs/amazon-bedrock)。

## OSS 模式（本地提供方）

传入 `--oss` 后，Codex 可以使用 Ollama 或 LM Studio 等本地“开源”提供方。单次运行可通过 `--local-provider` 选择提供方，也可用 `oss_provider` 设置默认值。如果两者都没有设置，交互式 CLI 会要求你选择；`codex exec` 则会报错退出。

<CodeBlock code={"# `--oss` 默认使用的本地提供方\noss_provider = \"ollama\" # 或 \"lmstudio\""} language="toml" />

## Azure 提供方与按提供方微调

<CodeBlock code={"[model_providers.azure]\nname = \"Azure\"\nbase_url = \"https://YOUR_PROJECT_NAME.openai.azure.com/openai\"\nenv_key = \"AZURE_OPENAI_API_KEY\"\nquery_params = { api-version = \"2025-04-01-preview\" }\nwire_api = \"responses\"\nrequest_max_retries = 4\nstream_max_retries = 10\nstream_idle_timeout_ms = 300000"} language="toml" />

如果你只是想修改内建 OpenAI 提供方的基础 URL，请使用 `openai_base_url`，不要创建 `[model_providers.openai]`，因为内建提供方 ID 不能被覆盖。

## 启用了数据驻留的 ChatGPT 客户

如果你的项目启用了 [数据驻留](https://help.openai.com/en/articles/9903489-data-residency-and-inference-residency-for-chatgpt)，可以创建一个模型提供方，把 `base_url` 换成[正确前缀](https://platform.openai.com/docs/guides/your-data#which-models-and-features-are-eligible-for-data-residency)。

<CodeBlock code={"model_provider = \"openaidr\"\n[model_providers.openaidr]\nname = \"OpenAI Data Residency\"\nbase_url = \"https://us.api.openai.com/v1\" # 将 us 替换为对应地域前缀"} language="toml" />

## 审批策略与沙箱模式

你可以同时配置审批严格程度（控制 Codex 何时暂停）和沙箱级别（控制文件 / 网络访问范围）。

在编辑 `config.toml` 时，和这些设置相关的运行时行为细节可参考 [常见的沙箱与审批组合](/docs/agent-approvals-security#common-sandbox-and-approval-combinations)、[可写根目录中的受保护路径](/docs/agent-approvals-security#protected-paths-in-writable-roots) 和 [网络访问](/docs/agent-approvals-security#network-access)。

如果要使用同时配置文件系统和网络访问的 Beta（测试版）权限配置档案，请参见[权限](/docs/permissions)。

你也可以使用细粒度审批策略，也就是 `approval_policy = { granular = { ... } }`，按类别允许或自动拒绝单独的提示。这适合你希望某些情形仍保留交互式批准，而另一些情形，例如 `request_permissions` 或技能脚本提示，则默认直接拒绝的场景。

如果你希望把符合条件的交互式审批请求交给自动评审，可以设置 `approvals_reviewer = "auto_review"`。这只会改变由谁来评审，不会改变沙箱边界。

本地评审策略指令可以写在 `[auto_review].policy` 里。若管理员下发了 `guardian_policy_config`，则以托管策略为准。

<CodeBlock code={"approval_policy = \"untrusted\"   # 其他可选值：on-request、never 或 { granular = { ... } }\napprovals_reviewer = \"user\"     # 也可以设为 \"auto_review\"，启用自动评审\nsandbox_mode = \"workspace-write\"\nallow_login_shell = false       # 可选加固项：禁止 shell 工具使用 login shell\n\n# 细粒度审批策略示例：\n# approval_policy = { granular = {\n#   sandbox_approval = true,\n#   rules = true,\n#   mcp_elicitations = true,\n#   request_permissions = false,\n#   skill_approval = false\n# } }\n\n[sandbox_workspace_write]\nexclude_tmpdir_env_var = false  # 允许使用 $TMPDIR\nexclude_slash_tmp = false       # 允许使用 /tmp\nwritable_roots = [\"/Users/YOU/.pyenv/shims\"]\nnetwork_access = false          # 如需出站网络访问，请显式开启\n\n[auto_review]\npolicy = \"\"\"\nUse your organization's automatic review policy.\n\"\"\""} language="toml" />

## Shell 环境策略

`shell_environment_policy` 控制 Codex 会把哪些环境变量传给它启动的命令。可以通过 `inherit = "none"` 从空环境开始，也可以使用 `inherit = "core"` 继承一组精简变量。再添加显式值与按键过滤器，避免把不必要的敏感信息传给命令。

<CodeBlock code={"[shell_environment_policy]\ninherit = \"core\"\nset = { MY_FLAG = \"1\" }\nignore_default_excludes = false\n\n[shell_environment_policy.filters]\n\"AWS_*\" = \"exclude\"\n\"AZURE_*\" = \"exclude\""} language="toml" />

过滤模式不区分大小写，并支持 `*` 和 `?`。使用 `"exclude"` 删除匹配的变量。当任一模式使用 `"include"` 时，Codex 只保留匹配 include 模式的变量。include 不会恢复先前已排除的变量。不同配置层中的过滤键以不区分大小写的方式合并。

`ignore_default_excludes` 默认为 `true`，因此 Codex 不会自动删除名称中包含 `KEY`、`SECRET` 或 `TOKEN` 的变量。将其设为 `false` 后，会先应用这些自动排除规则，再运行显式过滤器。

Codex 依次应用自动排除、自定义排除、`set` 中的值，最后应用 include 模式的 allowlist。由于 `set` 在排除之后执行，它可以恢复已排除的变量；但 include allowlist 仍可能再次移除该值。

旧版 `exclude` 和 `include_only` 数组仍受支持。不要在同一配置层中将其中任一数组与 `[shell_environment_policy.filters]` 混用，否则 Codex 会拒绝该配置。

## 可观测性与遥测

你可以启用 OpenTelemetry（OTel）日志导出，用来追踪 Codex 运行过程，包括 API 请求、SSE 事件、提示词、工具审批和工具结果。该功能默认关闭；如需启用，请在 `[otel]` 中配置：

<CodeBlock code={"[otel]\nenvironment = \"staging\"   # 默认为 \"dev\"\nexporter = \"none\"         # 设为 otlp-http 或 otlp-grpc 以发送事件\nlog_user_prompt = false   # 默认脱敏用户提示词，除非显式开启"} language="toml" />

你可以选择导出器：

<CodeBlock code={"[otel]\nexporter = { otlp-http = {\n  endpoint = \"https://otel.example.com/v1/logs\",\n  protocol = \"binary\",\n  headers = { \"x-otlp-api-key\" = \"${OTLP_TOKEN}\" }\n}}"} language="toml" />

<CodeBlock code={"[otel]\nexporter = { otlp-grpc = {\n  endpoint = \"https://otel.example.com:4317\",\n  headers = { \"x-otlp-meta\" = \"abc123\" }\n}}"} language="toml" />

如果 `exporter = "none"`，Codex 仍会记录事件，但不会发送出去。导出器会异步批量发送，并在退出时刷新。事件元数据中会包含服务名、CLI 版本、环境标签、会话 ID、模型、沙箱 / 审批设置，以及按事件不同而扩展的字段，详见 [配置参考](/docs/config-file/config-reference)。

### 会发出哪些事件

Codex 会发出结构化日志事件，用于描述运行过程和工具调用。代表性的事件类型包括：

-   `codex.conversation_starts`：记录模型、推理设置以及沙箱 / 审批策略
-   `codex.api_request`：记录请求次数、状态 / 是否成功、耗时和错误详情
-   `codex.sse_event`：记录流式事件类型、成功 / 失败、耗时，以及在 `response.completed` 时附带的 token 统计
-   `codex.websocket_request` 和 `codex.websocket_event`：记录请求耗时，以及每条消息的类型 / 是否成功 / 错误信息
-   `codex.user_prompt`：记录长度；除非显式开启，否则内容会被脱敏
-   `codex.tool_decision`：记录是批准还是拒绝，以及决定来自配置还是来自用户
-   `codex.tool_result`：记录耗时、是否成功和输出片段

### 匿名指标上报

默认情况下，Codex 会定期向 OpenAI 回传少量匿名使用与健康状态数据。这些数据有助于识别 Codex 何时工作异常，也能让团队了解哪些功能和配置正在被实际使用，从而把精力投入到最重要的问题上。这些指标不包含任何个人身份信息（PII）。需要注意的是，指标收集与 OTel 日志及 trace 导出彼此独立。

如果你想在某台机器上的 ChatGPT 桌面应用、Codex CLI 和 IDE 扩展中彻底关闭指标收集，可在配置中设置分析数据上报开关 `analytics`：

<CodeBlock code={"[analytics]\nenabled = false"} language="toml" />

每个指标除自身字段外，还会带上下面这些默认上下文字段。

### 反馈控制

默认情况下，本地客户端允许用户通过 `/feedback` 发送反馈。如果你想在某台机器上的 ChatGPT 桌面应用、Codex CLI 和 IDE 扩展中关闭反馈提交，可更新配置：

<CodeBlock code={"[feedback]\nenabled = false"} language="toml" />

关闭后，`/feedback` 会显示不可用提示，并且 Codex 会拒绝反馈提交。

### 隐藏或显示推理事件

如果你想减少“推理”输出带来的噪音，例如出现在 CI 日志中，可以压制它：

<CodeBlock code={"hide_agent_reasoning = true"} language="toml" />

如果你想在模型有输出时显示原始推理内容：

<CodeBlock code={"show_raw_agent_reasoning = true"} language="toml" />

只有当你的工作流能够接受原始推理内容暴露时才建议开启。某些模型 / 提供方，例如 `gpt-oss`，并不会输出原始推理内容，这种情况下该设置不会产生可见效果。

## 通知

你可以使用 `notify`，在 Codex 发出受支持事件时触发一个外部程序（目前仅支持 `agent-turn-complete`）。这很适合接入桌面通知、聊天 webhook、CI 状态更新，或任何内建 TUI 通知没有覆盖到的旁路提醒。

<CodeBlock code={"notify = [\"python3\", \"/path/to/notify.py\"]"} language="toml" />

下面是一个会响应 `agent-turn-complete` 的 `notify.py` 示例（节选）：

<CodeBlock code={"#!/usr/bin/env python3\nimport json, subprocess, sys\n\ndef main() -> int:\n    notification = json.loads(sys.argv[1])\n    if notification.get(\"type\") != \"agent-turn-complete\":\n        return 0\n    title = f\"Codex: {notification.get('last-assistant-message', 'Turn Complete!')}\"\n    message = \" \".join(notification.get(\"input-messages\", []))\n    subprocess.check_output([\n        \"terminal-notifier\",\n        \"-title\", title,\n        \"-message\", message,\n        \"-group\", \"codex-\" + notification.get(\"thread-id\", \"\"),\n        \"-activate\", \"com.googlecode.iterm2\",\n    ])\n    return 0\n\nif __name__ == \"__main__\":\n    sys.exit(main())"} language="python" />

该脚本会收到一个单独的 JSON 参数。常见字段包括：

-   `type`：当前为 `agent-turn-complete`
-   `thread-id`：会话标识符
-   `turn-id`：当前轮次的标识符
-   `cwd`：工作目录
-   `input-messages`：触发这一轮的用户消息
-   `last-assistant-message`：助手最近一条消息的文本内容

把脚本放到磁盘上的任意位置，然后让 `notify` 指向它即可。

#### `notify` 与 `tui.notifications`

-   `notify` 用于运行外部程序，适合接 webhook、桌面通知程序或 CI 钩子。
-   `tui.notifications` 是 TUI 内建的通知机制，也可以按事件类型过滤，例如 `agent-turn-complete` 或 `approval-requested`。
-   `tui.notification_method` 用于控制 TUI 发送终端通知的方式，可选值为 `auto`、`osc9` 或 `bel`。
-   `tui.notification_condition` 用于控制 TUI 通知只在终端 `unfocused` 时触发，还是设为 `always` 后无论焦点状态都触发。

在 `auto` 模式下，Codex 会优先使用 OSC 9 通知。它是一种终端转义序列，某些终端会把它解释为桌面通知；如果不可用，则会退回到 BEL（`\x07`）。

具体键名见 [配置参考](/docs/config-file/config-reference)。

## 历史记录持久化

默认情况下，Codex 会把本地会话记录保存到 `CODEX_HOME` 下，例如 `~/.codex/history.jsonl`。如果你要关闭本地历史记录持久化：

<CodeBlock code={"[history]\npersistence = \"none\""} language="toml" />

如果你想限制历史文件大小，可设置 `history.max_bytes`。当文件超过上限后，Codex 会丢弃最旧条目，并在保留最新记录的前提下压缩文件。

<CodeBlock code={"[history]\nmax_bytes = 104857600 # 100 MiB"} language="toml" />

## 可点击引用

如果你的终端 / 编辑器集成支持，Codex 可以把文件引用渲染为可点击链接。通过配置 `file_opener`，可指定 Codex 使用哪种 URI 方案：

<CodeBlock code={"file_opener = \"vscode\" # or cursor, windsurf, vscode-insiders, none"} language="toml" />

例如，像 `/home/user/project/main.py:42` 这样的引用，就可以被改写成可点击的 `vscode://file/...:42` 链接。

## Desktop

本节选项仅适用于 ChatGPT 桌面 App。

### 添加自定义文件处理器

在用户级 `~/.codex/config.toml` 中，为 `desktop.custom_file_handlers` 添加条目，即可用 ChatGPT 桌面 App 默认不支持的编辑器或内部启动器打开文件。每个条目都会在 App 的 **Open in（打开方式）** 菜单中增加一个编辑器目标。若 `command` 是现有绝对路径，或能从 App 的 `PATH` 中解析，App 就会列出该目标。

下面的示例展示三种向 handler 传递文件的方式：

<CodeBlock code={"# 把打开的路径直接追加到命令后。\n[desktop.custom_file_handlers.vscodium]\nlabel = \"VSCodium\"\nicon = \"/Users/you/.codex/icons/vscodium.png\"\ncommand = \"codium\"\n\n# 在打开的路径前放置固定参数。\n[desktop.custom_file_handlers.textedit]\nlabel = \"TextEdit\"\nicon = \"/Users/you/.codex/icons/textedit.png\"\ncommand = \"/usr/bin/open\"\nargs = [\"-a\", \"TextEdit\"]\n\n# 追加一个包含路径和编辑器上下文的 JSON 参数。\n[desktop.custom_file_handlers.company_editor]\nlabel = \"Company Editor\"\nicon = \"/opt/company/editor/icon.png\"\ncommand = \"/opt/company/bin/editor\"\ninput = \"json_argument\""} language="toml" />

保存 `config.toml`，然后重启 ChatGPT 桌面 App。

handler ID 是 TOML 表头的最后一段。长度必须为 1–64 个字符，以 ASCII 字母或数字开头，其余字符只能使用 ASCII 字母、数字、句点、下划线或连字符。App 会为 ID 添加 `custom:` 前缀，例如 `company_editor` 会变成 `custom:company_editor`。包含句点的 ID 必须加引号，避免 TOML 将其解释为嵌套表。例如：

<CodeBlock code={"[desktop.custom_file_handlers.\"company.editor\"]\nlabel = \"Company Editor\"\nicon = \"/opt/company/editor/icon.png\"\ncommand = \"/opt/company/bin/editor\""} language="toml" />

每个 handler 支持以下字段：

<div className="doc-table-wrap">

| 字段 | 必填 | 说明 |
| --- | :-: | --- |
| `label` | 是 | App 中显示的名称。 |
| `icon` | 是 | 内建 App 图标（如 `apps/vscode.png`）、Base64 `data:image/...` URL、`file:` URI 或本地图片绝对路径。不支持的来源会使用默认 VS Code 图标。 |
| `command` | 是 | 用于检测并启动的可执行文件路径或命令名。 |
| `args` | 否 | 插入在 `command` 与文件输入之间的字符串数组，默认为 `[]`。 |
| `input` | 否 | App 传递文件输入的方式：`path`、`json_argument` 或 `json_stdin`，默认为 `path`。 |
| `supports_ssh` | 否 | 是否为 SSH 工作区中的文件提供该 handler，默认为 `false`。当 handler 需要远程 host 和路径详情时，请使用 `json_stdin`。 |

</div>

`input` 的值决定 `args` 之后的内容：

-   `path`：把路径追加为最后一个命令参数。
-   `json_argument`：追加一个包含 `target`、`path`、`appPath` 和 `location` 的 JSON 对象。`location` 是包含从 1 开始计数的 `line`、`column` 的对象，也可以是 `null`。
-   `json_stdin`：把 JSON 对象写入标准输入，而不是追加参数。对象还包含 `hostConfig`、`remoteWorkspaceRoot` 和 `remotePath`；不适用时这些字段为 `null`。

例如，当用户打开特定源码位置时，`company_editor` 可以收到以下参数：

<CodeBlock code={"{\n  \"target\": \"custom:company_editor\",\n  \"path\": \"/repo/src/index.ts\",\n  \"appPath\": null,\n  \"location\": { \"line\": 12, \"column\": 3 }\n}"} language="json" />

把自定义 handler 选为首选编辑器后，App 会像内建编辑器一样保存该选择，包括项目级偏好。

## TUI 选项

直接运行 `codex` 而不带子命令时，会启动交互式终端界面（TUI）。Codex 在 `[tui]` 下提供了一些 TUI 专属配置项，包括：

-   `tui.notifications`：启用或关闭通知，也可以限制只接收特定类型的通知
-   `tui.notification_method`：选择终端通知方式，可用值为 `auto`、`osc9` 或 `bel`
-   `tui.notification_condition`：选择通知只在终端失焦时触发，还是始终触发；可用值为 `unfocused` 或 `always`
-   `tui.animations`：启用或关闭 ASCII 动画与闪光效果
-   `tui.alternate_screen`：控制是否使用备用屏幕（alternate screen）；设为 `never` 时会保留终端滚动历史
-   `tui.show_tooltips`：控制欢迎页是否显示引导提示

`tui.notification_method` 默认值为 `auto`。在 `auto` 模式下，如果 Codex 判断当前终端支持，它会优先使用 OSC 9 通知。OSC 9 是一种终端转义序列，有些终端会把它解释为桌面通知；如果不可用，则会退回到 BEL（`\x07`）。

完整键列表请参见 [配置参考](/docs/config-file/config-reference)。
